# Changelog

## v1.3.0

Fixes every finding from the post-v1.2.0 (PR #70) audit rounds except finding 11 (an overly strict incoming `"ss"` frame length check), which stays intentionally deferred at the maintainer's own request: loosening it safely needs two-step remote training so position tracking stays in sync with whatever a shorter frame actually represents - a separate, larger piece of work than this release's scope, still open for a future release, not forgotten. Entries below are in finding-number order (11 skipped on purpose), followed by one unrelated typo fix, a new feature, and one further fix found by auditing that new feature once it shipped. Released as a minor version (not a patch) because it bundles a new feature alongside the audit fixes - semver reserves a patch bump for fixes alone.

* Check `control_blind_stop()`'s return value in `_async_position_update_loop()`'s auto-stop-at-target branch (`cover.py`) instead of unconditionally clearing `is_opening`/`is_closing`/the pending target the instant it's called. Previously, if that stop write failed outright - a USB hiccup, or another blind's pairing/teach/raw-transmit holding `_pairing_active` at that exact moment - the motor kept running past the intended stop point to its own physical end stop, while Home Assistant had already torn down the tracking state that would have let it recognize and react to a later real stop. The entity was then left reporting whatever position it had estimated at the failed-stop instant, permanently wrong, with the motor's own eventual end-stop confirmation discarded by the STOPPED handler's early return (`is_opening`/`is_closing` already `False`). Now a failed send logs a warning naming the device and target, and `continue`s the polling loop with tracking state intact, so the very next tick retries the stop - and a later genuine STOPPED echo, whether from this retry or the motor's own end stop, is still recognized normally. New test `test_position_loop_retries_auto_stop_when_the_write_fails` (`tests/test_cover.py`) mocks `control_blind_stop` to fail once, then confirms the loop keeps `is_opening` true and the target intact, and calls it again on the next tick. Audit finding 1.

* Clear `self._target_position` in `async_open_cover()`'s and `async_close_cover()`'s own failure paths (`cover.py`), alongside the existing `is_opening`/`is_closing`/`_move_start_time`/`_move_start_position` resets, when a `set_cover_position()` leg that asked to preserve its target (`_preserve_target=True`) fails to send. Previously, a leftover target from that failed leg stayed in `self._target_position` with no move actually in flight to clear it later - and a subsequent, completely unrelated move (typically triggered by the original remote control, not by Home Assistant) could read that stale, long-invalid target back via `_async_position_update_loop()`'s own auto-stop-at-target check and get prematurely stopped there, short of wherever the remote itself was actually sending it. Distinct from the already-documented secondary-remote-control direction limitation, which is about a different mechanism entirely. The redundant-resend branch earlier in each method (where the original move's own target is still genuinely live) already returns before reaching this point, so clearing unconditionally here is safe. New tests `test_async_open_cover_clears_stale_target_when_a_preserved_leg_fails` and `test_async_close_cover_clears_stale_target_when_a_preserved_leg_fails` (`tests/test_cover.py`). Audit finding 2.

* Make a timed-out or errored calibration leg's retry actually recapture status frames instead of silently discovering nothing. `_set_calibration_capture_phase()` (`options_flow_calibration.py`) now checks a new `self._capture_active` flag before labelling the active capture's phase; previously, every error exit from either calibration leg tore the capture down via `_finish_calibration_capture()`, but a retry re-entering the same step only reset the UI's own phase state, and `api.py`'s `set_status_frame_capture_phase()` silently no-ops once no capture is open - so the retry looked like it succeeded (no error shown) while actually recording zero frames, leaving the blind at "status unknown" with no position tracking and nothing pointing back at the earlier timeout as the cause. Now, when no capture is active, the method starts a fresh one via `_start_calibration_capture()` instead of labelling a capture that no longer exists - and because that fresh start can itself lose the shared capture buffer to a different blind's own flow (see finding 6 below), `_set_calibration_capture_phase()` now returns a bool, and `async_step_calibration_open_instruction()`/`async_step_calibration_close_instruction()` both show the new `calibration_capture_busy` error and stay on the same step rather than assuming a retry always succeeds. New test `test_open_instruction_retry_after_timeout_reopens_the_capture` (`tests/test_options_flow_calibration.py`). Audit finding 3.

* Protect an already-confirmed blind's working status identity from being silently erased by an inconclusive "Determine status from original remote" attempt. The reconfigure flow's save step in `config_flow.py` previously wrote `CONF_STATUS_IDENTITY_SOURCE`/`CONF_SECONDARY_STATUS_IDENTITIES` unconditionally and popped `CONF_STATUS_DEVICE_ID`/`CONF_STATUS_ENUM` whenever discovery found nothing - with no distinction between "nothing was there to begin with" and "something was there and discovery just didn't catch it this time" (wrong button, pressed too fast, RF interference). A new `elif` branch now checks, via `normalize_status_identity()`, whether a valid identity already exists and its source isn't already `STATUS_IDENTITY_SOURCE_UNKNOWN`; if so, it logs an info line and leaves `data` completely untouched instead of erasing the existing mapping, mirroring the protection `async_step_calibration_complete()` already has for its own analogous "discovered nothing" case. The plain "nothing existed, nothing found" case still records `STATUS_IDENTITY_SOURCE_UNKNOWN` as before. New test `test_discover_status_finding_nothing_keeps_the_existing_identity` (`tests/test_config_flow.py`). Audit finding 4.

* Bound `control_blind_stop()`'s final ack-wait (`api.py`) to whatever is actually left of its own `STOP_RETRY_BUDGET`, via `ack_wait_timeout = min(MOVE_ACK_TIMEOUT, max(deadline - time.monotonic(), 0.0))`, instead of always waiting the full, fixed `MOVE_ACK_TIMEOUT` (1.0s) regardless of how much budget lock contention from another near-simultaneous blind command had already spent. Previously the method could overrun its own documented 2.0s budget by up to that same ~1s margin; in practice the stop write itself had normally already reached the wire by then (the shutter still stopped on time, visible only via the method's own warning log lines), but if the write itself - not just its ack - was what got lost, a retry really could delay the physical stop by a similar margin. `asyncio.wait_for(timeout=0)` still returns immediately rather than raising, so the clamp to a non-negative value needs no special-casing. The identical unbounded-wait pattern exists in the ordinary move-retry path (`control_blind_with_retry`), but stays untouched there - its much larger `MOVE_RETRY_OVERALL_TIMEOUT` (15.0s) makes the same slip immaterial. New test `test_control_blind_stop_bounds_the_ack_wait_to_the_remaining_budget` (`tests/test_api.py`). Audit finding 5.

* Stop one blind's calibration or status-discovery flow from forcibly stealing another blind's in-progress status-frame capture on the same hub. `_start_calibration_capture()` (`options_flow_calibration.py`) previously caught `start_status_frame_capture()`'s `RuntimeError` and forced its way in anyway - finishing and discarding whatever capture was already open, then starting its own in its place - which let two concurrent flows for two *different* blinds (nothing in the integration prevents two subentry wizards running at once) silently corrupt each other's result: a frame meant for one blind's capture could land in the other's buffer, and whichever flow finished last received whichever buffer happened to be live, not necessarily its own - for a brand-new pairing specifically, with no existing identity to sanity-check against, the wrong identity could reach permanent config data with zero warning. `_start_calibration_capture()` now returns `False` on that `RuntimeError` instead of stealing, and all three call sites (`async_step_calibration_initial_state`, `async_step_calibration_open_instruction`, `async_step_calibration_close_instruction`) check it and show a new `calibration_capture_busy` error (added to `strings.json` and all four `translations/*.json` files) rather than silently proceeding on a capture that isn't theirs. `async_discover_status_identities()` in `config_flow.py` already let the same `RuntimeError` propagate correctly and needed no change. `_finish_calibration_capture()`/`_set_calibration_capture_phase()` also now read back from a new `self._capture_api` field - the specific `SchellenbergUsbApi` instance a capture actually started on - rather than re-fetching `entry.runtime_data`, which doubles as finding 15's fix for this same buffer. New tests `test_calibration_close_busy_error_does_not_steal_capture_buffer` and `test_open_retry_busy_error_when_another_capture_took_the_buffer` (`tests/test_options_flow_calibration.py`). Audit finding 6 - see also finding 23 below, resolved as a side effect of this same fix.

* Close the hub-wide move-ack slot (`_move_awaiting_ack`/`_move_ack_event`/`_move_ack_result` in `api.py`) to every caller that used to write via `control_blind()` directly, unlocked, while an ordinary move or stop already held `_move_lock` and that same slot. The wire protocol carries no correlation id, so `_handle_message()`'s t1/t0/tE handling attributes any reply to whichever call currently has `_move_awaiting_ack` set - safe only if at most one write is outstanding against the slot at a time, an invariant `_move_lock` already enforced move-vs-move and move-vs-stop, but not against four other call sites that bypassed it entirely: `config_flow.py`'s motor-direction test and its stop (`async_step_test_motor`), the reconfigure wizard's "Test open/close/stop" (`_async_developer_command()`), the post-teach open+stop test (`async_step_teach_motor`), and `__init__.py`'s `_handle_test_command()` backing the public `schellenberg_usb.test_command` service. A real write to any of these while another blind's ordinary move was mid-ack-wait could have the stick's reply for the test misattributed to that other move, including a spurious "busy" that risks a real duplicate RF transmission on retry. New `control_blind_exclusive()` method in `api.py` now backs all four call sites: it takes `_move_lock` like an ordinary (non-priority) move, sets up the same ack-wait slot, calls `control_blind()`, and waits up to `MOVE_ACK_TIMEOUT` for any reply - accepted or busy, it doesn't matter which, since `control_blind()` never gave these callers ack feedback to begin with - before releasing the lock, so that reply is consumed here rather than risking a late arrival after the lock is released. No retry-on-busy semantics were added, deliberately, to avoid the transmitter contention `control_blind()`'s own one-write-immediately design exists to avoid. New tests `test_control_blind_exclusive_sends_and_returns_true_on_accept`, `test_control_blind_exclusive_returns_false_when_the_write_itself_fails`, `test_control_blind_exclusive_returns_true_on_a_silent_ack_timeout`, `test_control_blind_exclusive_does_not_steal_another_blinds_ack_slot`, and `test_control_blind_exclusive_serializes_two_calls_instead_of_racing` (`tests/test_api.py`). Confirmed this does not corrupt pairing/teach/raw-transmit's own retry bookkeeping, since `control_blind()` already refuses to write at all while `_pairing_active` is set. Audit finding 7 - probably the most practically significant fix in this release.

* Make `cover.py`'s own status-identity resolution in `async_setup_entry()` match `identities.py`'s canonical `resolve_blind_identities()`: when `status_identity_source == STATUS_IDENTITY_SOURCE_UNKNOWN`, `status_device_id`/`status_enum` are now set to `None` outright instead of being read back out of the subentry's possibly-stale `CONF_STATUS_DEVICE_ID`/`CONF_STATUS_ENUM` fields. An `UNKNOWN` source means "no confirmed primary status identity," regardless of whatever values are still sitting in config data from before it became unconfirmed - previously, that stale value briefly reached `api.register_entity()` as this entity's primary status identity, immediately corrected a moment later by `SchellenbergCover`'s own re-derivation in `async_added_to_hass()` (which already has its own correct `STATUS_IDENTITY_SOURCE_UNKNOWN` check), but never retracted in between. Not reachable through the current UI - every write path already clears these fields together - only with hand-edited or legacy config data. New test `test_async_setup_entry_nulls_a_stale_status_identity_when_source_is_unknown` (`tests/test_cover.py`). Audit finding 8.

* Extend the cross-blind interference protection calibration already had for its "movement detected" wait to the actual identity decision too. `summarize_status_discovery_frames()` (`identities.py`) gains an `exclude_device_ids` keyword-only parameter: frames from any of these ids are now excluded from grouping and primary/secondary selection entirely, not merely deprioritized, while still counting toward the capture's own total frame count for diagnostic transparency. `finish_status_frame_capture()` (`api.py`) forwards it through (defaulting to empty, so both `async_discover_status_identities()` call sites, which deliberately never scope this, are unaffected), and `_finish_calibration_capture()` (`options_flow_calibration.py`) now passes the same `foreign_capture_device_ids` set `_wait_for_movement_start()` already used. Previously, if an already-paired, normally-working blind moved - its own automation, its own remote - while a *different* blind was being calibrated, that other blind's real frames could win the race on frame count and get wrongly stored as the identity of the blind actually being calibrated, with none of the collision checking manual identity editing already has. New test `test_calibration_excludes_other_blinds_frames_from_identity_result` (`tests/test_options_flow_calibration.py`). Audit finding 9.

* Make the USB-stick (hub) device's own "Download diagnostics" button in Home Assistant's UI actually return stick data instead of a generic error. `async_get_device_diagnostics()` (`diagnostics.py`) previously only ever matched `SUBENTRY_TYPE_BLIND` subentries - skipping the hub's own `SUBENTRY_TYPE_HUB` subentry (created by `__init__.py`'s `async_setup_entry()` for the stick device itself) outright, so a diagnostics request from the hub device's own page could never match anything and always fell through to `{"error": "No blind subentry found for device ..."}`, even though `_stick_diagnostics()` - already used by the entry-level diagnostics download - was sitting right there unused for this path. Now checks `async_device_on_subentry_compat()` first regardless of subentry type, then branches on `SUBENTRY_TYPE_BLIND` vs `SUBENTRY_TYPE_HUB` to call `_blind_diagnostics()` or `_stick_diagnostics()` respectively; the fallback error message is reworded from "No blind subentry found" to "No subentry found" to match. New test `test_device_diagnostics_returns_the_hub_sticks_state` (`tests/test_diagnostics.py`). Audit finding 10.

* Cap `SchellenbergProtocol`'s per-connection receive buffer (`api.py`) at a new `MAX_SERIAL_BUFFER_LENGTH = 4096` bytes. `data_received()` previously only ever grew `self.buffer` looking for a `"\n"`, with nothing draining it otherwise; a flaky USB-CDC connection, a firmware glitch, a brownout, or a misconfigured port that stopped producing a clean line terminator would grow it without limit for as long as that lasted - and since Python strings are immutable, every `+=` onto it re-copies the whole buffer, so per-chunk CPU cost grew right along with memory. Every message this integration actually parses is well under 64 bytes, so 4096 is a sanity ceiling normal operation should never approach, not a tuned budget. Once exceeded with no terminator found, `data_received()` now logs a warning and resets `self.buffer = ""`, discarding the stuck partial line and starting fresh rather than growing forever; a reconnect already cleared this via a fresh `SchellenbergProtocol` instance and still does. Five new tests in `tests/test_api.py` - `test_data_received_parses_a_message_split_across_two_chunks`, `test_data_received_parses_multiple_messages_in_one_chunk`, `test_data_received_keeps_buffering_a_partial_line_under_the_cap`, `test_data_received_resets_the_buffer_once_it_exceeds_the_cap_without_a_terminator`, and `test_data_received_cap_is_measured_after_draining_complete_lines` - cover both the pre-existing chunking/multi-message behavior (previously untested directly) and the new cap. Audit finding 12.

* Validate and bound `_last_received_messages` (`api.py`), which previously accepted any identity `_handle_message()` built from raw, unvalidated substrings of a decoded line - unlike every other identity in this integration, which goes through `identities.normalize_status_identity()` - and grew without limit, surviving a reconnect, for as long as a noisy RF environment kept producing distinct spurious or corrupted frames. New `_record_last_received_message()` helper now gates the write on `normalize_status_identity()` succeeding, and bounds the dict to a new `MAX_LAST_RECEIVED_MESSAGES = 64` constant, evicting whichever identity has gone longest without being re-seen (pop-then-reinsert on a plain dict, which preserves insertion order, so the true least-recently-updated key is always `next(iter(...))`) rather than simply the first ever seen. `_handle_message()` now calls this helper instead of writing the dict directly, and `handle_connection_lost()`/`disconnect()` both now also `.clear()` this cache, matching how every other piece of per-connection state there is already reset. New tests `test_handle_message_does_not_cache_an_ss_frame_with_a_non_hex_device_id`, `test_handle_message_evicts_the_oldest_identity_once_the_cache_is_full`, `test_handle_message_moves_a_re_seen_identity_back_to_the_front_of_the_cache`, `test_handle_connection_lost_clears_the_last_received_message_cache`, and `test_disconnect_clears_the_last_received_message_cache` (`tests/test_api.py`). Audit finding 13.

* Cap `_status_discovery_frames` (`api.py`) at a new `MAX_STATUS_DISCOVERY_FRAMES = 1000` per capture window, logging a debug line and dropping the rest once hit rather than appending without limit for as long as a capture window (up to 300s/45s, per `CALIBRATION_TIMEOUT`/`STATUS_DISCOVERY_TIMEOUT`) stays open. A real open/close leg or remote-discovery sequence produces at most a handful of frames per device, so 1000 is a generous multiple, not a tuned budget - this was the lower-confidence/lower-severity half of the original finding, since `summarize_status_discovery_frames()` already only reads real signal out of whatever the list holds and the window always closes and discards it regardless, so garbage frames could never masquerade as a real identity either way; the cap closes the remaining, purely-memory-growth concern during sustained RF interference. New test `test_handle_message_caps_the_status_discovery_frame_list` (`tests/test_api.py`). Audit finding 14.

* Stop a sibling blind's subentry reload from orphaning an in-progress calibration capture on the same hub. Every subentry add/remove/edit reloads the whole hub config entry, replacing `entry.runtime_data` with a brand-new `SchellenbergUsbApi` instance; `_set_calibration_capture_phase()`/`_finish_calibration_capture()` (`options_flow_calibration.py`) previously re-fetched `entry.runtime_data` fresh on every call with no caching, so a reload landing between a capture's start and finish handed finish the *new*, never-started instance - empty, nothing to read - while the *old* instance, which had actually buffered the blind's real frames, was silently dropped; degrades gracefully (no live position feedback) rather than corrupting an existing identity, but silent either way, with nothing pointing at the reload as the cause. A new `self._capture_api` field now caches the specific API instance a capture actually started on (set in `_start_calibration_capture()`, cleared once the capture finishes), and both methods read from it instead of re-deriving it - the same class of hazard the codebase had already fixed for `_fresh_calibration_positions`, a different piece of per-instance state, just never extended to this buffer. New test `test_calibration_capture_survives_a_reload_mid_flow` (`tests/test_options_flow_calibration.py`). This pass deliberately does not address the finding's smaller, separate secondary observation - a reload caused by a sibling blind mid-pairing being reported as an ordinary "pairing timeout" rather than identified as a reload - which stays open for a future release. Audit finding 15.

* Cancel a blind's own in-flight move or stop the moment its subentry/device is removed, instead of leaving it running until the side-effect hub reload's unload phase eventually reaches `disconnect()` - which, unlike this, wakes every blind on the hub, not just the removed one. Home Assistant's generic subentry-deletion UI triggers only the same generic full reload as any other subentry change; `cover.py` previously cancelled only its own position-polling task on removal, with no task handle kept anywhere for the move/retry loop itself. `async_will_remove_from_hass()` now also calls `self._api.cancel_pending_move(self._command_device_id)` - the same per-device mechanism `async_stop_cover()` and the auto-stop-at-target path already use - before shutting down position tracking; a no-op when nothing is in flight, the common case for most removals, so safe to call unconditionally like every other `cancel_pending_move()` call site. Closes the window where a just-deleted blind's retry loop could still transmit a real RF command, or process a stray ack, for a blind Home Assistant no longer has an entity for. New test `test_will_remove_from_hass_cancels_this_devices_in_flight_move` (`tests/test_cover.py`). Audit finding 16.

* Recalculate the STOPPED-event position log line (`cover.py`'s `_handle_event()`) after `_update_position()`'s own recalculation and clamp, not before. The `_LOGGER.info("Device %s STOPPED (position: %d%%)", ...)` call previously ran immediately after capturing `previous_position`, ahead of the recalculation the rest of the handler goes on to use - so it always printed the position as of the last 0.2s polling tick (or the move's starting position, if STOPPED arrived before the tracking loop ever ticked), never the freshly recalculated value. Every real field - `self._attr_current_cover_position` itself, and `_record_position_update()`'s `new_position` just below, which already reads it post-recalculation - was always correct, so this was purely a diagnostics-only log lag, never a functional bug. New test `test_handle_event_stopped_logs_the_recalculated_position` (`tests/test_cover.py`). Audit finding 17.

* Cap `_async_position_update_loop()`'s `stop_lead_percent` latency-compensation calculation (`cover.py`) at a new `MAX_STOP_LEAD_PERCENT = 50.0` constant (`const.py`), via `min((STOP_COMMAND_LATENCY_SECONDS / travel_time_for_lead) * 100, MAX_STOP_LEAD_PERCENT)`. The calculation's divisor, `travel_time_for_lead`, was already floored at 0.1s to avoid a division blow-up, but the result itself had no matching ceiling - for any real shutter, whose travel time is measured in seconds to tens of seconds, the lead this produces is a small single-digit percentage nowhere near the cap, but for a travel time so short or corrupted that the uncapped lead ran into the hundreds of percent, the position-reached check it feeds would be satisfied by any position at all the instant a move started, however far it actually was from `target_position`. New test `test_position_loop_caps_the_stop_lead_for_a_very_short_travel_time` (`tests/test_cover.py`), using a 1.0s configured travel time (an uncapped lead of 120%) to confirm the loop no longer stops instantly. Audit finding 18.

* Close a startup race in `SchellenbergLedSwitch.async_added_to_hass()` (`switch.py`) between restoring the LED's last known state and a concurrently-firing dispatcher signal. The dispatcher subscription was previously registered *before* the `await self.async_get_last_state()` call that restores `self._is_on` - a suspension point a concurrently-arriving status-update signal could observe mid-await, reading stale, pre-restore state. Restoration now happens before the subscription is registered, closing that race, and a second, smaller one alongside it: `self._was_available = True` now runs before, not after, the subsequent `await self._restore_hardware_state()`, rather than after it. The original nested condition (`if last_state is not None and self.api.is_connected:`, gating the hardware-push) is preserved exactly, so a connected switch with no state to restore still correctly leaves `_was_available` `False`, matching the existing `test_added_to_hass_defaults_to_off_with_nothing_restored` test. New test `test_added_to_hass_does_not_race_the_restore_against_a_concurrent_reconnect` (`tests/test_switch.py`) fires the real dispatcher signal mid-await via a custom `racing_get_last_state()` stand-in to reproduce the exact race. What looked like a brief, self-correcting LED flicker at startup was a genuine race, not just inherent hardware behavior. Audit finding 19.

* Remove the dead `title` key from `options.step.init` in `strings.json` and all four `translations/{en,de,es,fr}.json` files. Home Assistant's options flow never reads a step's `title` from translations for this integration's single-step `init` flow - it's rendered from the config entry's own title instead - so this key, identical across all four languages anyway, was never actually shown. Confirmed via a full audit of every other seemingly-standalone key in `runtime_translation_text.py` first (`block_disconnected`, `block_wrong_mode`, the bare `"Yes"`/`"No"` literals, and others) that a naive cross-file grep made look dead too - all of those are genuinely live, produced internally by that file's own `translate_block_reason()`/`yes_no()` helpers rather than referenced as literal strings elsewhere, so none of them were touched. All five files re-verified as valid JSON with matching 153-key parity after the removal. No test referenced the removed key, so none needed adapting. Audit finding 20.

* Show `--` instead of the literal word `None` for a freshly-set-up or just-restarted blind's position fields in the "Copy diagnostics" text export (`config_flow.py`'s `async_step_copy_diagnostics()`). A new local `_position_text()` helper (`"--" if value is None else f"{value}%"`) now wraps all three affected call sites - `diag_previous_position`, `diag_new_position`, and `diag_current_estimated_position` (which shares `new_position`'s own field, read a second time for the confidence section) - mirroring the placeholder handling `_developer_snapshot()`'s own live dev-tools panel already had for the same two underlying fields. Only `diag_previous_position` was named in the original finding, but `diag_new_position`/`diag_current_estimated_position` shared the identical root cause (`get_last_position_update()`'s own fallback dict explicitly sets both `previous_position` and `new_position` to `None` for a device with zero recorded history) and were equally wrong for the same blind. New test `test_copy_diagnostics_shows_dashes_not_none_with_no_position_history` (`tests/test_config_flow.py`). Audit finding 21.

* Add a hub-level `EVENT_HOMEASSISTANT_STOP` listener in `__init__.py`'s `async_setup_entry()`, registered via `entry.async_on_unload(hass.bus.async_listen_once(EVENT_HOMEASSISTANT_STOP, _async_handle_hass_stop))`, which calls `await api.disconnect()`. `async_unload_entry()` already disconnects the stick cleanly on an ordinary reload/remove/disable, but Home Assistant does not call that for every loaded entry on a full Core stop/restart - until now, only `cover.py`'s own per-entity listener ran at that point, freezing each blind's own position estimate but leaving the hub's shared serial connection itself open for process teardown to close however it happened to. Low-impact even before this fix - nothing buffered to flush, and HA's own shutdown sequence cancels remaining tasks anyway - but now gets the same clean, intentional close a reload already triggers. New test `test_async_setup_entry_disconnects_the_api_on_hass_stop` (`tests/test_init.py`) fires a real `EVENT_HOMEASSISTANT_STOP` event and awaits `hass.async_block_till_done()`, proving registration and handling together rather than calling the handler function directly. Audit finding 22.

* No dedicated fix needed: `"superseded_by_calibration"`'s only producing code path - the capture-stealing branch finding 6 above removes entirely - no longer exists, so the translation value it used to (uselessly) produce is now unreachable by construction rather than merely unused. Confirmed the only remaining reference to `"superseded_by_calibration"` anywhere in the repository is inside `AUDIT_FINDINGS.md`'s own description text. Audit finding 23, resolved as a side effect of finding 6's fix.

* Set `self._last_transmit_source = source` in `control_blind()` (`api.py`), right before it writes straight to the transport. `send_command()` already does this for every command it routes through `_pending_retry_command`/`_last_transmit_source`, but `control_blind()`'s whole reason to exist (see its own docstring) is writing directly instead, bypassing `send_command()` - and with it, this assignment - entirely. Without it, a t1/t0 reply arriving after a `control_blind()` write (and before any other, `send_command()`-routed one) would log, and self-heal `_busy_latched` under, whichever *earlier* caller last went through `send_command()` instead of this one. Diagnostic/log-attribution only - `_busy_latched` is documented as never blocking a new command regardless, so nothing functional depended on this. New test `test_control_blind_updates_last_transmit_source` (`tests/test_api.py`). Audit finding 24.

## v1.1.4

* Fix several blinds commanded together still occasionally losing a command even with v1.1.3's "wait for transmitter idle" fix (see below) - that fix narrowed the race window but did not close it, confirmed from a real log of six blinds commanded together: all six observed the transmitter idle between the same two ACKs and all wrote within 15ms of each other, of which the stick accepted exactly one (`t1`) and answered `tE` to the other five - which `control_blind()` still neither waited for nor retried, so those five still vanished rather than merely arriving late. Root cause: waiting for idle and then writing were two separate steps, and `asyncio.Event.set()` (what `wait_for_transmitter_idle()` waits on) wakes every waiter at once, not one at a time, so several blinds racing the same shared event could all pass the wait and all reach their own write before any of them learned whether the stick had actually accepted it. `async_open_cover()`/`async_close_cover()` now call a new `control_blind_with_retry()` (`api.py`) instead of `wait_for_transmitter_idle()` + `control_blind()`: it holds a new, dedicated `_move_lock` across the *entire* write-then-retry-until-accepted cycle for one blind at a time, not just the write, so a second blind's call genuinely queues behind the first instead of racing it for the one write that matters, and retries on `tE` endlessly - same no-retry-limit policy as `send_command()`'s own busy-retry cycle, independent machinery: routing moves through that cycle's own single-slot `_pending_retry_command`/`_retry_task` bookkeeping was tried once before and a second contending move silently clobbered the first's retry tracking, which this new, separate lock/event pair structurally cannot do. `async_stop_cover()` now calls the also-new `cancel_pending_move()` as the very first thing in its body, before any `await`, so a stop ends that same blind's own still-retrying move loop instead of letting an already-queued retry resend the open/close command after the stop has already gone out - the exact collision that made an earlier attempt at routing moves through the busy-retry cycle get reverted before `control_blind()` was made deliberately instant/unretried for open, close, and stop alike (see that method's own docstring). The auto-stop-at-target path in the position-tracking loop calls `cancel_pending_move()` too, right before it sends its own stop, for the same reason. `control_blind()` itself is unchanged - both of these are still the same one unlocked, unretried write each. Covered by new `test_api.py` cases proving two blinds queue rather than race for the wire, the endless-retry policy, a silently-timed-out ack being treated the same as a busy reply, and `cancel_pending_move()`'s cancellation/no-op/wrong-device behavior; new and updated `test_cover.py` cases confirm `async_open_cover()`/`async_close_cover()` now call `control_blind_with_retry()`, and that `async_stop_cover()` and the auto-stop-at-target path both call `cancel_pending_move()` before their own stop write.

* Fix a `set_cover_position()` leg queued behind other blinds in the new `_move_lock` above being able to have its target evaluated as already reached purely from time spent waiting for that lock, not from any actual travel - found while reasoning through how that same lock interacts with the position-tracking loop for a short leg in a multi-blind burst; not yet confirmed from a real log, unlike the fixes below. Root cause: `async_open_cover()`/`async_close_cover()` used to set `_move_start_time`/`_move_start_position` and start the background tracking loop *before* awaiting `control_blind_with_retry()`, right when the method was first called - so a call still waiting its turn on the hub-wide lock already had its elapsed-time estimate running, counting that wait as travel time. For a short enough leg queued behind enough other blinds in the same burst, the estimate could reach the target - triggering the loop's own early stop - before this blind's own open/close command had been transmitted even once; `cancel_pending_move()` cannot catch that case either, since it is a no-op until the device actually holds `_move_lock`, which a still-queued call has not yet done. The real command would then go out once its turn came, with no tracking left running to stop it at the target - it would keep moving under that command all the way to the physical end stop instead. `_move_start_time`/`_move_start_position` and the tracking loop now only start once `control_blind_with_retry()` has actually succeeded, never before. Covered by two new `test_cover.py` cases (`test_async_open_cover_does_not_start_tracking_before_retry_succeeds` and its close-cover mirror) proving neither the clock nor the tracking loop is set/started while a stand-in retry call is still "in flight".

* Fix `control_blind_with_retry()`'s endless busy-retry (see above) being able to hold the hub-wide `_move_lock` open-endedly if one blind's own stick interaction stayed persistently busy or never acked at all - not yet confirmed from a real log, found while auditing the integration for other effects of that same lock after the queued-move fix above. Before that fix, `control_blind()` itself was always instant and independent per blind, so one blind's own hardware trouble never affected any other; holding `_move_lock` for the *whole* retry cycle (needed to close the dropped-command race above) introduced a new coupling where every other blind's own open/close now queues behind whichever one is still retrying - with no limit on how long that could take. The number of attempts is still unlimited - that part is deliberate and unchanged, since in practice a busy reply resolves within tens of milliseconds (see `MOVE_ACK_TIMEOUT`'s own comment) - but elapsed time spent holding the lock is now capped by a new `MOVE_RETRY_OVERALL_TIMEOUT` (15s, `api.py`): past that, the call gives up, releases the lock, and latches `busy_latched`, the same diagnostic flag `send_command()`'s own exhausted-retry path already sets, so the existing `busy_latched` block reason explains the failure in the UI without a new translation string. The clock only starts once a call actually holds `_move_lock` - time spent queued behind other blinds, still waiting to acquire it in the first place, is ordinary queueing and never counted against this budget. Covered by a new `test_api.py` case proving the loop gives up and latches `busy_latched` once a fake clock crosses the deadline, independent of how many attempts happened; the existing unlimited-attempts test is renamed and reworded to be clear that it is attempt count, not elapsed time, that has no limit.

* Fix the fine-position-control example scripts (README's "Optional: fine position control" section) overshooting small `set_cover_position` targets - confirmed from real use: a target around 7% that landed precisely before `control_blind_with_retry()` above only lands reliably from about 14% upward since. For a short move `rest_dauer` is already clamped to 0, so that difference is the entire remaining budget, and it drifts straight into overshoot - worst for the smallest, most common fine adjustments. No integration code changed; this is the README's example `scripts.yaml` only.

* Fix the fix directly above still not being enough for the smallest `set_cover_position` targets - confirmed from real use across four blinds: reliable from 14% upward, 17% for one of them, each tested closing from fully open. Root cause: recomputing `rest_dauer` from how long the double-send actually took cannot claw back time the double-send itself already spent before that recomputation even runs - and the fixed one-second gap between the two sends alone, let alone the now-variable wait for each send's own reply, was already close to a short move's entire travel time even before `control_blind_with_retry()` existed. For a target close enough to the start that `dauer` is shorter than that preamble, the blind is already past it before the script starts counting down `rest_dauer` at all, and no later correction can undo movement that already happened. The gap between the two sends is now 0.3s instead of 1, and the second send is skipped entirely - no gap, no repeat command - whenever `dauer` is below a new, per-call `min_fahrzeit_doppel` (default 3s, both scripts): a short move gets exactly one send and keeps its precision budget intact, a longer move keeps today's full double-send unchanged. `min_fahrzeit_doppel` is read with `{{ min_fahrzeit_doppel | default(3) | float(3) }}`, not just `| float(3)` - confirmed from real use that the plain `float(3)` form still raises `UndefinedError` and aborts the whole script run before its first `open_cover`/`close_cover` when a call omits the field entirely, rather than falling back to its default, since Jinja's `Undefined` reaches `float()` before `float()` ever gets a chance to catch anything. No integration code changed; this is the README's example `scripts.yaml` only, again.
