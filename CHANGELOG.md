# Changelog

## v1.4.0

Follows v1.3.0, starting with a real-world auto-stop reliability fix plus two issues an independent review found in it, and one unrelated timeout increase.

* **Real-world report:** a six-blind Alexa "25%" voice command (2026-11-01) left one blind (Wohnzimmerrolladen) fully closed in reality while its dashboard card stayed frozen at 68%, reported live with two dashboard warning screenshots plus a fresh log capturing the exact reproduction. Root cause: `control_blind_stop()` (`api.py`) returned a bare `bool`, collapsing two genuinely different outcomes into the same truthy value - the stick explicitly accepting the stop write ("t1"), and `STOP_RETRY_BUDGET` (2.0s) running out and falling back to one last, completely unlocked, unretried `control_blind()` write with no idea whether the stick (let alone the motor) ever saw it. Both call sites treated any truthy result as "this blind has now stopped": in this reproduction, the fallback fired for the living-room blind, `_async_position_update_loop()`'s auto-stop-at-target branch finalized on the strength of it - clearing `is_opening`/`is_closing`/the tracking state and freezing `_attr_current_cover_position` at whatever `_update_position()` had last estimated (68%) - and the blind then kept physically closing, uncontrolled, all the way to its own end stop; the real, later confirming "STOPPED" activity event that did eventually arrive (8.4s afterward, per the reproduction's own log) could not correct this, since `_update_position()`'s own first line (`if self._move_start_time is None or self._move_start_position is None: return`) is a no-op once that tracking state is already torn down.

  `control_blind_stop()` now returns a new three-member `StopOutcome` enum (`CONFIRMED`/`UNCONFIRMED`/`FAILED`) instead of a bare `bool`, with its own docstring explaining why `CONFIRMED` and `UNCONFIRMED` must never collapse back into one truthy value. `FAILED` covers exactly the old bare `False` (not even the fallback write reached the wire); `CONFIRMED` the old bare `True` for a stick-accepted write; `UNCONFIRMED` is new - the fallback fired, and bytes almost certainly reached the wire, but nothing confirms the stick ever saw them.

  First, `_async_position_update_loop()`'s auto-stop-at-target branch (`cover.py`): its existing safe "don't finalize, retry next tick" pattern - previously triggered only by a hard `FAILED` outcome - now also covers `UNCONFIRMED`, bounded by a new, deliberately much more generous backstop than `STOP_RETRY_BUDGET` itself: `AUTO_STOP_CONFIRMATION_BACKSTOP_SECONDS` (`const.py`), tracked per-episode via a new `self._pending_auto_stop_since` timestamp (see the third paragraph below for exactly how that stays correctly scoped to one episode). A drop to 15.0s was considered and explicitly decided against (2026-11-07) in favour of keeping the original, more generous 30.0s margin. Once the backstop genuinely elapses with still no confirmation, the loop gives up for real: `_attr_current_cover_position` and `_attr_is_closed` are set to `None` - Home Assistant's own "unknown" representation, already used elsewhere in this integration - rather than left on the stale, already-snapped target percentage, `_position_source_kind` is set to `"unconfirmed - backstop exhausted"`, and `is_opening`/`is_closing`/the tracking state/the target are all cleared the same way a confirmed stop already clears them. New tests `test_position_loop_retries_auto_stop_when_the_write_is_unconfirmed` (mirrors the existing `FAILED` regression test, proving `UNCONFIRMED` retries exactly the same way) and `test_position_loop_backstop_reports_unknown_after_prolonged_unconfirmed_stops` (a fake clock proves one early `UNCONFIRMED` still retries, and one that pushes total elapsed past the backstop reports position `None` instead) (`tests/test_cover.py`).

  Second, `async_stop_cover()` (`cover.py`, a manual stop): deliberately does *not* gain the same retry - a physical/dashboard stop press must stay responsive, not wait up to the backstop's own 30s for a confirmation that may never come, and `control_blind_stop()` already retries internally for up to `STOP_RETRY_BUDGET` regardless of caller. `FAILED` still raises `HomeAssistantError` exactly as the old bare `False` did. `UNCONFIRMED` now completes the same way `CONFIRMED` does - the estimate is still frozen via `_update_position()`, exactly as before - but `_position_source_kind` is set to `"unconfirmed stop"` instead of `"HA command"`, and a new warning is logged, rather than this being indistinguishable from a confirmed stop the way it was before `StopOutcome` existed. New test `test_async_stop_cover_reports_unconfirmed_without_raising` (`tests/test_cover.py`).

  Third, an independent review of the two paragraphs above (2026-11-01, verified firsthand rather than taken on trust) found `self._pending_auto_stop_since` was only ever cleared on a `CONFIRMED` outcome or the backstop's own exhaustion - never when the tracking task was torn down any other way (`_async_cancel_position_tracking()`/`_stop_position_tracking()`, e.g. a direction reversal landing mid-retry), nor when `self._target_position` changed to `None` while the same task kept running past a retarget. A stale timestamp left over from one episode could then survive into a completely different, later one and silently eat into (or exhaust outright) its own backstop budget before that episode's very first attempt - fail-safe in direction (position gets reported unknown too early, never trusted too long), but real, and reachable through the ordinary case of changing direction mid-contention, not just the original six-blind reproduction. Fixed two ways: `_async_cancel_position_tracking()` and `_stop_position_tracking()` now clear `self._pending_auto_stop_since` (and a new, paired `self._pending_auto_stop_target`) unconditionally whenever either is called, and - belt and suspenders, covering the same-task-no-cancellation case neither of those two methods is ever invoked for - the auto-stop branch itself now re-stamps both fresh whenever `self._pending_auto_stop_target` no longer matches the live `self._target_position`, rather than trusting whatever it finds. New test `test_position_loop_backstop_resets_after_a_retarget_mid_unconfirmed_retry` (`tests/test_cover.py`) proves a retarget landing mid-`UNCONFIRMED`-retry gives the new target its own full, fresh budget instead of inheriting however much of the old one was already spent.

  Fourth, the same review found `_handle_event()`'s own `STOPPED` log line (`cover.py`) formatted `self._attr_current_cover_position` with `%d%%`, which raises inside the logging module's own lazy formatting once the backstop exhaustion above sets it to `None` and a real, late `STOPPED` confirmation then still arrives from the stick - normally caught by a handler's own error handling rather than propagating, so this never crashed Home Assistant, but it did turn exactly the event this handler most needs to report cleanly into a confusing traceback instead. Now formats `None` as `"unknown"` rather than attempting `%d` on it. New test `test_handle_event_stopped_after_backstop_exhaustion_does_not_error` (`tests/test_cover.py`), which calls `record.getMessage()` directly to reproduce the exact failure mode rather than relying on whichever error-swallowing behaviour the test runner's own log capture happens to have.

  Every existing test across `tests/test_api.py` and `tests/test_cover.py` that mocks or asserts on `control_blind_stop()`'s return value was updated to use the matching `StopOutcome` member instead of a bare `bool` (no behavior change) - including a new sibling test, `test_control_blind_stop_reports_failed_when_even_the_fallback_write_fails` (`tests/test_api.py`), for the one sub-case nothing previously exercised directly: the exhausted-fallback write itself also failing to reach the wire, which must stay `FAILED`, not get folded into the same `UNCONFIRMED` a landed-but-unacked write gets.

  Verified with ruff (clean, both `check` and `format --check`) and a full-project mypy baseline diff against the last committed revision (identical error counts, zero new) across every file this entry touches; not yet verified against a real pytest run, for the same already-documented reason as the entries below (no network for `uv sync`/`uv sync --offline` in this sandbox).

* `MOVE_RETRY_OVERALL_TIMEOUT` (`api.py` - the overall budget `control_blind_with_retry()` spends retrying a move command, hub-wide, before giving up) raised from 15.0s to 30.0s (2026-11-07, project owner's own direction) for more headroom under this installation's real, heavier multi-blind contention than the original figure assumed. Every existing test that exercises this budget already references the constant symbolically (`api_module.MOVE_RETRY_OVERALL_TIMEOUT`) rather than a hardcoded `15.0`, so none needed changing - confirmed by inspection, not just assumed. Verified with ruff and the same mypy baseline-diff method as above.

* **Evaluated before implementing, per explicit direction:** whether a blind's own "ss" status frames (the same primary-identity echo `_handle_event()` already listens for) could give `control_blind_with_retry()`/`control_blind_stop()`'s command-retry logic a more precise, motor-level confirmation than the one-hop stick ack those two currently settle for - `motor_result=unknown`, always, per `STOP_COMMAND_EXTRA_RESENDS`'s own comment in `const.py`. Traced the full receive path (serial `data_received()` → line split → "ss" parse → `async_dispatcher_send` → `_handle_event()`) and found no code-side delay anywhere, for either a move or a stop frame - both are dispatched synchronously, in the same tick the bytes arrive. A real log gathered for this evaluation (2026-11-07) then showed where the ~1.5s the project owner had observed for Gurtwickler move frames actually comes from: a paired remote's secondary-identity "button held" frames repeating roughly every 0.11s, with the matching primary-identity confirmation landing only 0.55-0.89s after the *last* repeat for a stop, but a full ~1.46s after the *first* repeat for a move - almost certainly the physical button needing to be held for a real stretch before the motor commits to a move at all, not anything in this integration's own code. Decided with the project owner (2026-11-07) to scope this to the stop side only: gating `control_blind_with_retry()`'s own move confirmation on a frame that lags this far behind the triggering action would cost materially more latency per move for no corresponding gain, and risks a double-send if `MOVE_RETRY_OVERALL_TIMEOUT`'s own retry fires before a delayed frame ever catches up.

  Implemented for the stop side: a new `MANUAL_STOP_MOTOR_CONFIRMATION_GRACE_SECONDS` (2.0s, `const.py`) and a new `self._pending_manual_stop_confirmation` (`cover.py`, an `asyncio.Event | None`). `async_stop_cover()` creates it before calling `control_blind_stop()` (so a frame arriving during that call's own internal waits is never missed), and - only once that call returns `StopOutcome.CONFIRMED` - additionally waits up to the new grace period for `_handle_event()`'s `EVENT_STOPPED` branch to set it, which that branch now does unconditionally, the same way it already unconditionally calls `cancel_pending_move()`. When the frame arrives in time, `_handle_event()` has by then already done the complete, more-authoritative update itself (position recalculated at the true stop moment, `_position_source_kind` set to `"primary status"`, recorded with `status="confirmed"`) and `async_stop_cover()` does nothing further for that case. On timeout - most plausibly real RF interference, per the project owner's own explicit requirement that this never cost reliability - this falls through to exactly the stick-ack-only handling that existed before this feature did, byte for byte: the command is still fully processed, nothing hangs, only the extra confidence is missing. `UNCONFIRMED` outcomes skip the wait entirely, unchanged from before, for the same "a manual stop must stay responsive" reasoning `async_stop_cover()`'s own docstring already gave for not retrying on `UNCONFIRMED`.

  Of the existing tests that mock `control_blind_stop()` returning `CONFIRMED` and drive it through `async_stop_cover()`, four whose assertions only concern calls made *during* that mocked call (`test_async_stop_cover_sends_stop_via_control_blind_stop`, `test_async_stop_cover_cancels_a_pending_move_for_this_device_first`, `test_async_stop_cover_does_not_itself_wait_for_transmitter_idle`, `test_async_stop_cover_clears_target_before_awaiting_control_blind_stop`) now have their mock side effect also fire the motor echo immediately, so they exercise (and are unaffected by) the new fast path instead of needlessly waiting out the real grace period. Two whose assertions specifically depend on the post-wait fallback tail running (`test_async_stop_cover_does_not_cancel_tracking_before_stop_succeeds`, `test_async_stop_cover_freezes_position_from_elapsed_time_after_stop_returns`) instead shorten the grace period itself to 0.0 via `monkeypatch`, deliberately without firing the echo, since firing it would take the new early-return path and skip the exact tail behavior each of those two already exists to verify. New tests: `test_handle_event_stopped_sets_the_pending_manual_stop_confirmation` and `test_handle_event_stopped_with_no_pending_confirmation_does_not_error` (`_handle_event()`'s own new line, in isolation); `test_async_stop_cover_treats_a_prompt_motor_echo_as_more_authoritative` (end-to-end: a real `_handle_event(EVENT_STOPPED)` call from inside the mocked `control_blind_stop()`, not a raw `Event.set()` shortcut, proving the position comes from that handler's own calculation); `test_async_stop_cover_falls_back_cleanly_when_no_motor_echo_arrives` (the RF-interference case: `CONFIRMED` with no echo ever arriving still completes exactly as the old stick-ack-only path did, with a new debug log line) (all `tests/test_cover.py`).

  Verified with ruff (clean) and a full-project mypy baseline diff against the committed revision this builds on (34 errors in the three production files, 58 across production and tests both - identical counts, zero new, after fixing four genuinely new "Item `None` of `Event | None` has no attribute" errors mypy correctly caught in the new test closures' own `.set()` calls with an `assert ... is not None` first). Not yet verified against a real pytest run, for the same already-documented reason as the entries above.

* **Issue #78: position tracking visibly freezing for just over a second at the start of every single move, open/close included - not just an intermediate `set_cover_position()` leg.** Root cause: `async_open_cover()`/`async_close_cover()` (`cover.py`) pushed their own `self._move_start_time` forward by `STOP_COMMAND_LATENCY_SECONDS` (1.2s) at the start of every move. That push itself fixed a different, earlier bug (real log evidence, 2026-10-31: two blinds targeting an intermediate position stopped at ~82% after only ~2.2-2.6s, because the elapsed-time position *estimate* ran ahead of the real motor during the stick-accept-to-motor-start gap) - but combined with `_update_position()`'s own `elapsed_time = max(0.0, time.monotonic() - self._move_start_time)` clamp, it froze the reported position at the start position for that same 1.2s at the start of *every* move, intermediate target or not - on the dashboard, every open/close/set-position call appeared to "hang" for just over a second before showing any progress.

  Fixed by reverting the start-side push back to plain `time.monotonic()` (`async_open_cover()`/`async_close_cover()`, both call sites' own comments rewritten with the full history) and moving the same compensation to where part of it already lived: `_async_position_update_loop()`'s own `stop_lead_percent` calculation, which only ever applies to an intermediate `set_cover_position()` target (never to a plain open/close running to the true 0/100 end stop, which has no stop command of its own to compensate for in the first place). Its base compensation is now `STOP_COMMAND_LATENCY_SECONDS + STOP_COMMAND_LATENCY_SECONDS` (2.4s, was 1.2s), with the pre-existing `move_lock_busy` contention widening still adding one more `STOP_COMMAND_LATENCY_SECONDS` on top of that (3.6s total when contended, was 2.4s) - the same one hardware-measured transmit-latency figure now covering both the original stop-side gap and the reverted start-side one together, costing nothing in precision versus applying it in two separate places, only in how early an intermediate stop fires - a cost intermediate-target stops already pay by design, unlike the reverted push's cost to every move regardless of target.

  `MAX_STOP_LEAD_PERCENT`'s own cap (50.0, unchanged) is, by this same doubling, now genuinely reachable by a real, uncorrupted short-travel blind rather than purely a guard against corrupt/legacy config data: any blind whose shorter of open/close travel time drops under roughly 7.2s would hit it on a contended stop. Checked directly against the project owner's own six real blinds (calibration data supplied directly, 2026-11-07): travel times range 8.45-23.27s, and the shortest (Badezimmerrolladen, 8.45s/8.90s) already produces a contended lead of ~43 points - comfortably under the cap, but no longer "nowhere near" it either; the other five have more headroom still.

  Also added, separate from the sluggishness fix itself but promised by the same issue: `_async_position_update_loop()` is now bounded by a new, outer `POSITION_UPDATE_LOOP_TIMEOUT_SECONDS` (120.0s, `const.py`) - a hard ceiling on this task's own total running time for one continuous tracking episode (captured once when the task starts, not re-based by a later retarget), checked every ~0.2s tick regardless of which branch the loop is currently in. This is deliberately a different, *outer* bound from the existing `AUTO_STOP_CONFIRMATION_BACKSTOP_SECONDS` (30.0s), which only times the auto-stop-at-target branch's own retry-`control_blind_stop()` sub-loop and never engages at all for a plain open()/close(); the new ceiling applies unconditionally, including to a plain open/close still waiting on its own full-travel resync, so a bug or a misconfigured travel time in any one branch cannot leave this task polling every 0.2s forever with the entity stuck reporting "opening"/"closing" and a position nobody can still vouch for. On expiry: the same "stop trusting a stale estimate, report the position as unknown instead" cleanup the existing backstop already does, plus clearing `self._full_travel_resync_direction`, which that narrower, auto-stop-only backstop never needed to touch. Set well above anything this loop is expected to actually take in practice - even the real travel times above plus a full `AUTO_STOP_CONFIRMATION_BACKSTOP_SECONDS` retry budget on top reach at most ~53s, and even `DEFAULT_TRAVEL_TIME_SECONDS`'s own generous un-calibrated fallback (60.0s) plus that same full retry budget only reaches 90s - so ordinary operation should never come close to tripping it; it exists purely as the backstop of last resort for whatever this fix's own doubled compensation, or some other interaction entirely, fails to anticipate.

  Tests (`tests/test_cover.py`): renamed `test_async_open_cover_pushes_move_start_time_past_the_dead_time` and its `close_cover` mirror to `test_async_open_cover_sets_move_start_time_to_plain_monotonic`/mirror, now asserting plain `time.monotonic()` instead of the removed push. `test_position_loop_stops_early_to_compensate_stop_latency`'s docstring numbers updated for the doubled lead. `test_position_loop_does_not_stop_before_the_compensated_lead` and `test_position_loop_widens_the_stop_lead_when_the_move_lock_is_busy` both have their fixture's `CONF_CLOSE_TIME` changed from 6.0s to 12.0s (at the doubled base, 6.0s would have pushed the compensated threshold past this test's own physically-possible position range for a closing blind); the busy-lock test's docstring is also corrected from "the lead doubles" to "the lead widens from 2x to 3x `STOP_COMMAND_LATENCY_SECONDS`", since the contended jump is now a 1.5x increase on the new base, not a literal doubling the way it was on the old one. `test_position_loop_caps_the_stop_lead_for_a_very_short_travel_time`'s docstring numbers updated to the new, doubled raw lead - the capped outcome itself is unchanged, both old and new raw leads already far exceeding the cap. `test_update_position_holds_at_start_during_the_transmit_dead_time`'s docstring rewritten to explain that neither call site constructs this scenario any more; the test itself now sets `_move_start_time` directly rather than via `async_open_cover()`/`async_close_cover()`, to keep verifying `_update_position()`'s own defensive clamp in isolation now that nothing in production still exercises it this way. New test `test_position_loop_times_out_after_the_outer_budget_is_exhausted` for the new outer ceiling, deliberately isolated from both the ordinary end-stop branch and the existing auto-stop backstop via a pinned position estimate that never satisfies either.

  Verified with ruff (clean) and a full-project mypy baseline diff against the committed revision this builds on (48 errors across `api.py`/`cover.py`/`const.py`/`tests/test_cover.py` combined - identical count, zero new, confirmed separately before and after the test-file changes). Not yet verified against a real pytest run, for the same already-documented reason as the entries above.

* **Issue #77: calibration "hanging endlessly"** (RolloDrive 65 Premium, reported 2026-11-07). Live calibration (`options_flow_calibration.py`) works by *listening* for the shutter's own movement-start/stop status frames while the person physically operates it - this integration sends no RF command of its own during calibration, see `calibration_open_instruction`/`calibration_close_instruction`'s own strings - so a frame that for whatever reason never arrives (a missed press, a weak signal, a remote on the wrong channel) left the wizard waiting on `CALIBRATION_TIMEOUT` (300s, 5 minutes) with nothing on screen to distinguish "still waiting" from "stuck", and no escape besides abandoning pairing outright. The default/legacy `pair_device` workflow (`config_flow.py`) was the most exposed case: unlike the "hybrid" `add_shutter_from_remote` workflow, which already offered a manual-entry alternative (`manual_times`) after its own motor test, legacy pairing went straight from naming the device into a live calibration with no alternative offered at all.

  `CALIBRATION_TIMEOUT` (`const.py`) lowered from 300 to 120 seconds (2 minutes) - still comfortably longer than any of the project owner's own six real blinds take to complete a leg (all finish within 24s, see `MAX_STOP_LEAD_PERCENT`'s own comment in the same file), but no longer a silent five-minute wait before the person sees anything at all. `CALIBRATION_TIMEOUT` and `PAIRING_TIMEOUT` are now deliberately equal (both 120s) rather than calibration keeping a larger margin over pairing, since calibration no longer needs that margin once it offers its own escape.

  Two new choices, both scoped to fresh pairing only via the existing `CalibrationFlowHandler._create_subentry_after_calibration` flag - recalibrating an already-paired blind (`async_step_calibrate()`, which calls `disable_subentry_creation()`) keeps its old, unchanged error-and-resubmit behavior, since that flow already has its own direct manual-entry escape one menu level up (reconfigure's own "edit" option), and `test_options_flow_calibration.py`'s own module docstring already scopes that whole file to the recalibration path alone, so none of its existing tests needed to change:

  - **Upfront choice before any live wait starts:** `pair_device`'s own workflow (`async_step_name_device()`'s legacy tail, `config_flow.py`) now shows a new `calibration_method_choice` menu - "Calibrate by moving the shutter" (`calibration_close`, the existing live flow, unchanged) or "Enter travel times manually" (`manual_times`) - instead of going straight into calibration. `manual_times` reuses the existing method built for the hybrid workflow as-is (collects open/close times directly, then `async_step_discover_status()`); that chain is fresh-pairing-only by its own existing comment ("there is no other caller") and only ever touches flow-level `_pending_*` state already set correctly by `async_step_name_device()` regardless of which path is chosen, so no changes were needed there.
  - **Choice on timeout, mid-calibration:** all four of `options_flow_calibration.py`'s own timeout branches (open/close leg x movement-start/stop wait) now check `_create_subentry_after_calibration` first; for a fresh pairing, a timeout now shows a `calibration_timeout_choice` menu - "Try again" (`calibration_retry`) or "Enter travel times manually" (`manual_times`) - instead of only an on-screen error and an implicit "submit this same form again". New `async_step_calibration_retry()` (both the handler's own version and its thin `config_flow.py` delegate) re-enters whichever leg is still pending (`self._open_time is None` decides, the same check the handler's own success tail already uses) rather than a hardcoded leg, so retrying after the close leg's own timeout doesn't send the person back to the already-finished open leg.

  `strings.json` and all four `translations/*.json` files updated for both new menu steps, plus the existing `calibration_timeout` error string's stale "5 minutes" corrected to "2 minutes" to match the lowered constant. Verified with a key-structure comparison across all five files (the only existing automated check, `test_calibration_close_forces_an_explicit_initial_state_choice`, checks just one specific step across languages) that `strings.json`/`en.json` stay content-identical and `de`/`es`/`fr` match the same key shape with translated values.

  Tests (`tests/test_config_flow.py`): `test_pairing_workflow_names_device_then_starts_calibration` and the shared helper `_drive_pairing_to_calibration_close()` updated to drive through the new `calibration_method_choice` menu first, so every existing test built on top of that helper stays correct. Three new tests: `test_manual_times_choice_creates_entry_directly` (the upfront choice reaches a real `CREATE_ENTRY` via the manual-entry path, mirroring hybrid's own equivalent test); `test_calibration_timeout_retry_targets_the_pending_leg` (drives a real open-leg completion between two shrunk-timeout retries, proving the retry targets whichever leg actually timed out rather than a hardcoded one - a hardcoded "always open_instruction" would wrongly pass the first retry and only fail on the second); `test_calibration_timeout_manual_choice_creates_entry` (abandoning a timed-out live attempt for manual entry also reaches a real `CREATE_ENTRY`, not just the upfront path). `tests/test_const.py`: `test_timeout_constants` updated for the new 120 value; `test_timeout_relationships`'s `CALIBRATION_TIMEOUT > PAIRING_TIMEOUT` relaxed to `>=`, with a comment explaining the two are now deliberately equal.

  Verified with ruff (clean, both `check` and `format --check`) and a full-project mypy baseline diff against the committed revision this builds on (19 errors in 3 files, 5 source files checked - identical count, zero new). Not yet verified against a real pytest run, for the same already-documented reason as the entries above.

* **Issue #78, a second fix from the same discussion thread: the pairing wizard offered two separate, confusingly-overlapping entry points for what is mechanically one action.** `async_step_user` (`config_flow.py`) used to be a menu choosing between "Pair and calibrate" (`pair_device`, the plain/default option - no motor-test confirmation, straight from naming into live calibration) and "Add device from remote (recommended)" (`add_shutter_from_remote` - taught the stick onto an already-paired remote's channel, then ran a motor test before calibration). The two options differed only in their own UI text and in whether a motor test ran first - `api.pair_device_and_wait()` itself already listens for either enrollment technique (a device's own pairing button, or a remote's programming button plus a stop command) regardless of which menu option a person picked, so the "legacy"/"hybrid" split this created was cosmetic, not functional, and it meant the un-recommended, default-sounding option was also the one offering less confirmation that pairing had actually worked.

  Resolved via direct confirmation with the project owner (2026-11-07) on how far this unification should reach, given the standing "no dead code" rule: all of the wizard's other menus stay exactly as they are, with the changes scoped to this one entry point and its immediate follow-ons. `async_step_user` is now the sole, unified pairing entry point - a single form ("Pair Device" / "Press the Pair button below, and then either press the pairing button on the device OR press the programming button on your already-paired remote control and afterwards send a stop command on your already-paired remote control to the motor you want to pair." / "Pair") covering both enrollment techniques in one description, with `async_step_pair_device()` and `async_step_add_shutter_from_remote()` both deleted outright rather than kept as now-unreachable code. The internal `self._pairing_workflow` tag that distinguished them collapses from `"legacy"`/`"hybrid"` to one `"pairing"` value (`"existing"`, the completely separate recalibration-of-an-already-paired-blind tag, is untouched). Every fresh pairing now reaches the same point `name_device` already led to for the old "hybrid" path: an unconditional `calibration_method_choice` menu ("Calibrate by moving the shutter" / "Enter travel times manually") - so the motor-test confirmation that used to be exclusive to the "recommended" option is now universal, not something the plainer-sounding option let a person skip. That menu's own `calibration_close` option is renamed `test_motor` (its label text is unchanged) to reflect that choosing it now always runs the motor test first, rather than going straight into live calibration the way it used to for this menu's old caller.

  One knock-on effect of moving the motor test earlier: `test_success`, previously a real two-way menu reached only after a successful motor test ("Enter travel times manually" as one of its own two options, alongside continuing to calibration), is left with nothing to offer as an alternative *to* - manual entry already moved earlier, to `calibration_method_choice`, before any motor test runs. * **Real-world report: a full up/down run landing on 92%/4% instead of 100%/0%, plus a separately-reported sluggish dashboard (2026-11-08).** Both traced to the same root cause: `control_blind_with_retry()`'s (`api.py`) `MOVE_COMMAND_EXTRA_RESENDS` resend loop ran inline, after the primary write's own accepted ack but before this method's own `return True` - blocking that return for an extra `MOVE_COMMAND_EXTRA_RESENDS * MOVE_COMMAND_RESEND_DELAY_SECONDS` seconds (~0.5s), during which `async_open_cover()`/`async_close_cover()` had not yet stamped `self._move_start_time` or started position tracking. ## v1.3.0

Fixes the post-v1.2.0 (PR #70) issues, followed by one unrelated typo fix, then several further fixes and withdrawals found afterward, ending with the withdrawal of a feature that shipped and was then withdrawn within this same release - see the last entry below for why this is still v1.3.0, a minor version, despite no longer adding one.

* Check `control_blind_stop()`'s return value in `_async_position_update_loop()`'s auto-stop-at-target branch (`cover.py`) instead of unconditionally clearing `is_opening`/`is_closing`/the pending target the instant it's called. Previously, if that stop write failed outright - a USB hiccup, or another blind's pairing/teach/raw-transmit holding `_pairing_active` at that exact moment - the motor kept running past the intended stop point to its own physical end stop, while Home Assistant had already torn down the tracking state that would have let it recognize and react to a later real stop. The entity was then left reporting whatever position it had estimated at the failed-stop instant, permanently wrong, with the motor's own eventual end-stop confirmation discarded by the STOPPED handler's early return (`is_opening`/`is_closing` already `False`). Now a failed send logs a warning naming the device and target, and `continue`s the polling loop with tracking state intact, so the very next tick retries the stop - and a later genuine STOPPED echo, whether from this retry or the motor's own end stop, is still recognized normally. New test `test_position_loop_retries_auto_stop_when_the_write_fails` (`tests/test_cover.py`) mocks `control_blind_stop` to fail once, then confirms the loop keeps `is_opening` true and the target intact, and calls it again on the next tick.

* Clear `self._target_position` in `async_open_cover()`'s and `async_close_cover()`'s own failure paths (`cover.py`), alongside the existing `is_opening`/`is_closing`/`_move_start_time`/`_move_start_position` resets, when a `set_cover_position()` leg that asked to preserve its target (`_preserve_target=True`) fails to send. Previously, a leftover target from that failed leg stayed in `self._target_position` with no move actually in flight to clear it later - and a subsequent, completely unrelated move (typically triggered by the original remote control, not by Home Assistant) could read that stale, long-invalid target back via `_async_position_update_loop()`'s own auto-stop-at-target check and get prematurely stopped there, short of wherever the remote itself was actually sending it. Distinct from the already-documented secondary-remote-control direction limitation, which is about a different mechanism entirely. The redundant-resend branch earlier in each method (where the original move's own target is still genuinely live) already returns before reaching this point, so clearing unconditionally here is safe *for this single-leg case* - a later fix further down found it was not safe against a different, concurrent leg's own live target landing in the same shared slot, and narrowed the clear accordingly; see that entry for the follow-up. ## v1.1.4

* Fix several blinds commanded together still occasionally losing a command even with v1.1.3's "wait for transmitter idle" fix (see below) - that fix narrowed the race window but did not close it, confirmed from a real log of six blinds commanded together: all six observed the transmitter idle between the same two ACKs and all wrote within 15ms of each other, of which the stick accepted exactly one (`t1`) and answered `tE` to the other five - which `control_blind()` still neither waited for nor retried, so those five still vanished rather than merely arriving late. Root cause: waiting for idle and then writing were two separate steps, and `asyncio.Event.set()` (what `wait_for_transmitter_idle()` waits on) wakes every waiter at once, not one at a time, so several blinds racing the same shared event could all pass the wait and all reach their own write before any of them learned whether the stick had actually accepted it. `async_open_cover()`/`async_close_cover()` now call a new `control_blind_with_retry()` (`api.py`) instead of `wait_for_transmitter_idle()` + `control_blind()`: it holds a new, dedicated `_move_lock` across the *entire* write-then-retry-until-accepted cycle for one blind at a time, not just the write, so a second blind's call genuinely queues behind the first instead of racing it for the one write that matters, and retries on `tE` endlessly - same no-retry-limit policy as `send_command()`'s own busy-retry cycle, independent machinery: routing moves through that cycle's own single-slot `_pending_retry_command`/`_retry_task` bookkeeping was tried once before and a second contending move silently clobbered the first's retry tracking, which this new, separate lock/event pair structurally cannot do. `async_stop_cover()` now calls the also-new `cancel_pending_move()` as the very first thing in its body, before any `await`, so a stop ends that same blind's own still-retrying move loop instead of letting an already-queued retry resend the open/close command after the stop has already gone out - the exact collision that made an earlier attempt at routing moves through the busy-retry cycle get reverted before `control_blind()` was made deliberately instant/unretried for open, close, and stop alike (see that method's own docstring). The auto-stop-at-target path in the position-tracking loop calls `cancel_pending_move()` too, right before it sends its own stop, for the same reason. `control_blind()` itself is unchanged - both of these are still the same one unlocked, unretried write each. * Fix the fine-position-control example scripts (README's "Optional: fine position control" section) overshooting small `set_cover_position` targets - confirmed from real use: a target around 7% that landed precisely before `control_blind_with_retry()` above only lands reliably from about 14% upward since. No integration code changed; this is the README's example `scripts.yaml` only.
